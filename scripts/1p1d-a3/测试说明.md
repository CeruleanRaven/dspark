# DeepSeek-V4.1-Flash-1017-w4a8-03-mtp 测试说明

权重目录：`/mnt/share/h00990513/models/DeepSeek-V4.1-Flash-1017-w4a8-03-mtp`。

服务脚本在同一目录：`start_container.sh`、`start_service.sh`。两台都是 A3。请求打到 Prefill 节点的 proxy：`http://<PREFILL_NODE_IP>:2999`，模型名 `dsv41`。

这次新权重只补验收表第 19、21、23、28 行。其余行用老权重已经测过的结果。

## 1. 这句话在说什么

「性能是用文档参数，测性能的数据集是用 gsm8k，测精度先用 gpqa 数据集」把测试拆成两件互不相干的事。

| | 性能 | 精度 |
| --- | --- | --- |
| 目的 | 填验收表右侧的时延、吞吐、QPS | 看答案对不对 |
| 服务怎么拉 | 用社区文档的 A3 1P1D 参数，也就是这两个脚本 | 同一套已经拉起来的服务 |
| 数据集 | GSM8K | 先用 GPQA |
| 长度、并发、请求数、前缀命中率 | 用验收表这一行的数字 | 不用验收表那一套并发 |
| 命令里有没有 `--mode perf` | 有 | 没有 |

两边不要对调。GSM8K 加了 `--mode perf` 出的是速度，不是分数。GPQA 不加 `--mode perf` 出的是分数，不是 TPOT。

## 2. 性能里的两个开关

性能有两层，容易看成一件事。

**第一层是文档参数，决定服务怎么跑、压测格子填多少。**

服务侧以 vLLM-Ascend 社区文档第 5.2.1 节为准，脚本里已经写好：

- 镜像 `quay.io/ascend/vllm-ascend:v0.30.0-a3`
- Prefill：`DP4 / TP1 / PCP4`，端口 7100–7103
- Decode：`DP16 / TP1`，端口 7100–7115
- 上下文长度 `1048576`
- DSpark 投机长度 5
- 权重用上面的 1017 W4A8 目录

压测侧用验收表这一行，不改服务参数：

- 平均输入、平均输出
- 总请求数、最大并发、请求频率
- PrefixCache（前缀命中率）

**第二层是数据集，决定题目从哪来。**

性能的数据集选 GSM8K。平台下拉框选 `gsm8k`，模式 `prefix_cache`，接口 `chat`。GSM8K 原题只有几百 token，输入长度要另填 131072。采样、前缀和 Warmup 以极光这条性能测试为准：

https://jiguang.ascend.huawei.com/inference/task/34bb532b-ca9b-4cbd-a133-8561d0839faa

任务名 `vLLM_PD分离_2机_dsv41_3级池化-mmc`。这条任务里的性能子任务共用下面这套，四行都按它填：

| 项 | 填法 |
| --- | --- |
| 数据集 | `gsm8k`，模式 `prefix_cache` |
| 接口 | `chat`，流式 |
| 采样 | `temperature=0.6, top_p=0.95` |
| 输入长度 | 131072 |
| Prefix Cache | 开 |
| 前缀数据集测试 | 开 |
| Repeat Rate 90 时的前缀长度 | 117964 |
| Warmup | 开。日志里是 `skip warmup: False` |
| 请求频率 0 | 不限制到达速度，用最大并发打满 |
| 卡数 | 16 |

请求频率、输出长度、并发、条数、Repeat Rate 仍按下面第 4 节这一行填。

## 3. 服务怎么起

先改 `start_service.sh` 顶部的 `PREFILL_NODE_IP`、`DECODE_NODE_IP`、`NIC_NAME`。两台机器用同一份。

```bash
# 两台都执行
bash start_container.sh

# Prefill 节点
bash start_service.sh prefill

# Decode 节点
bash start_service.sh decode

# 4 个 Prefill 和 16 个 Decode 都出现 Application startup complete 之后，在 Prefill 节点
bash start_service.sh proxy
```

后面的性能和精度都打 `http://<PREFILL_NODE_IP>:2999`。不要打某个引擎自己的 7100 端口。

## 4. 这次四行性能怎么填

四行打同一套 1P1D。数据集、采样、Prefix Cache、Warmup 用第 2 节那张共用表。每一行只改输出长度、并发、条数和 Repeat Rate。

| 行 | 在测什么 | 输入 | 输出 | 并发 | 条数 | 请求频率 | Repeat Rate | Prefix Cache | Warmup | 通过门槛 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 19 | 纯 P | 131072 | 1 | 42 | 168 | 0 | 90 | 开 | 开 | 卡 TTFT ≤ 10 秒 |
| 21 | 纯 D 高吞吐 | 131072 | 1024 | 1152 | 4608 | 0 | 100 | 开 | 开 | 卡 TPOT ≤ 50ms |
| 23 | 纯 D 低时延 | 131072 | 1024 | 144 | 576 | 0 | 100 | 开 | 开 | 卡 TPOT ≤ 20ms |
| 28 | 1P1D 完整体验 | 131072 | 1024 | 96 | 960 | 0 | 90 | 开 | 开 | 卡 TTFT ≤ 10 秒，卡 TPOT ≤ 20ms |

采样四行相同：`temperature=0.6, top_p=0.95`。数据集四行都是 `gsm8k` / `prefix_cache` / `chat`。

第 28 行在对照任务的「通用任务组 6」里有两次已完成记录，参数就是这一行：前缀条数 96，稳态重算开，Repeat Rate 90，生成的前缀长度 117964。第 19、21、23 行的输出长度、并发、条数和 Repeat Rate 按验收表。这条极光任务里的性能子任务输出都是 1024、Repeat Rate 都是 90，没有输出 1，也没有 Repeat Rate 100 的记录。

第 19 行输出长度是 1，只生成首 token。这一行没有后续 token，TPOT、ITL、输出吞吐留空。

第 21 行并发 1152，和 Decode 的上限相同：每个 rank `--max-num-seqs 72`，16 个 rank 一共 1152。

对照任务实际拉起 AISBench 的命令是：

```bash
ais_bench \
  --models vllm_api_chat_temp \
  --datasets gsm8k_gen_0_shot_cot_str_perf \
  --mode perf \
  --summarizer default_perf
```

输入长度、输出长度、并发、条数、请求频率和 Repeat Rate 在平台上填，不靠这条命令变成 131072。`--summarizer` 用的是 `default_perf`。通用任务组 6 的界面上，稳态重算是开的。

| 验收表的列 | 从性能结果里取 |
| --- | --- |
| TPOT 平均 (ms) | TPOT 的 Average |
| TPOT SLO_P90 (ms) | TPOT 的 P90 |
| ITL | ITL 的 Average，单位毫秒 |
| E2E 时间 (s) | E2EL 的 Average 除以 1000。这是单条请求的平均耗时 |
| 输入吞吐 (tps) | Input Token Throughput |
| 输出吞吐 (tps) | Output Token Throughput |
| E2E 吞吐 (tps) | Total Token Throughput，等于输入 token 加生成 token，再除以测试时长 |
| QPS | Request Throughput |
| 三个单卡吞吐 | 对应的总吞吐除以 16 |
| QPM | QPS 乘 60 |

卡 TTFT 表上没有写单位，按秒和门槛比。卡 TPOT 按毫秒比。`/` 的门槛不用比。采信率在性能结果里没有单独一列，这次不填。

和左边的门槛比对，通过的格子标绿。第 19 行只比 TTFT。第 21、23 行只比 TPOT。第 28 行 TTFT 和 TPOT 都比。

## 5. 精度先跑 GPQA

精度打同一套已经开了量化的 1P1D 服务。验收表标题要求必须开量化，`start_service.sh` 里的 `--quantization ascend` 要留着。数据集用 GPQA，不要先跑 GSM8K。不要加 `--mode perf`，也不要加 `--summarizer stable_stage`。看的是 accuracy，不是时延。

A3 PD 分离这一行的固定采样是：

- 输出长度 128k，也就是 `max_tokens=131072`
- `temperature=1.0`
- `top_p=1.0`
- `chat_template_kwargs={"thinking": true, "reasoning_effort": 100}`

`thinking` 打开思考，`reasoning_effort` 取 100，表示这档按最高推理力度出答案。对照任务是极光上这条：

https://jiguang.ascend.huawei.com/inference/task/34bb532b-ca9b-4cbd-a133-8561d0839faa

验收表里 A3 PD 分离的 GPQA 基线是 **89.5**。同一行已经有两次结果：91.41，以及约 91.24。单次大约要跑一个小时，多次之间会有小幅波动。这次的新权重也按这个采样跑，分数和 89.5 比。

数据放到 AISBench 的 `ais_bench/datasets/gpqa`。

```bash
ais_bench \
  --models vllm_api_general_chat \
  --datasets gpqa_gen_0_shot_str \
  --host-ip <PREFILL_NODE_IP> \
  --host-port 2999 \
  --model-name dsv41 \
  --generation-kwargs '{"temperature":1.0,"top_p":1.0,"max_tokens":131072,"chat_template_kwargs":{"thinking":true,"reasoning_effort":100}}'
```

GSM8K 精度不作为这次的第一项。社区文档里另有一个 A3 W4A8 的 GPQA 参考分 89.9，采样里没有 `reasoning_effort`。验收表这一行以 89.5 和上面这组参数为准。
